# Агрополия — аналитическая дорожная карта

**Статус:** рабочий проектный документ  
**Версия:** 1.0  
**Дата:** 2026-10-04  
**Назначение:** рабочая аналитическая дорожная карта для аналитика и разработчика.  
**Основание:** ФТЗ «Агрополия» v1.0 от 23.09.2026, принятые архитектурные поправки и текущая документация проекта.

> Этот документ **не заменяет и не редактирует ФТЗ**. Исходные приоритеты `P0 / P1 / P2` сохраняются неизменными. Документ вводит только внутреннюю последовательность подготовки и реализации требований проекта.

## 1. Как пользоваться дорожной картой

### 1.1. Два независимых измерения приоритета

В проекте одновременно используются два разных понятия:

| Понятие | Что означает | Можно ли менять этим документом |
|---|---|---|
| `P0 / P1 / P2` | Исходный продуктовый приоритет требования в ФТЗ | **Нет** |
| `Итерация 0 / 1 / 2 / 3 / 4` | Внутренняя последовательность аналитической подготовки и реализации | **Да, как рабочий план проекта** |

Требование может оставаться `P0` по ФТЗ и при этом быть запланировано на внутреннюю итерацию 2, 3 или 4. Это **не понижение приоритета и не изменение ФТЗ**, а декомпозиция большого P0-объёма на управляемые продуктовые контуры.

### 1.2. Источники истины

- требования, их смысл, ID и исходные `P0 / P1 / P2` — ФТЗ v1.0;
- принятые архитектурные уточнения — `docs/ftz-architecture-amendments-2026-10-01.md`;
- фактическая техническая декомпозиция нулевой итерации — `docs/i-0/iteration-0-scope-and-plan-2026-10-01.md`;
- фактический прогресс I-0 — `docs/i-0/worklog.md`;
- открытый технический blocker I-0 — `docs/i-0/capacitor-spike.md`;
- инструкции запуска/сборки — `README.md`.

Если новый продуктовый выбор противоречит ФТЗ или уже принятому проектному решению, он должен быть зафиксирован отдельно как решение, а не «растворён» в реализации.

## 2. Роли и разделение ответственности

### 2.1. Аналитик

Аналитик отвечает за:

- продуктовую дорожную карту;
- определение границ MVP и каждой внутренней итерации;
- пользовательские сценарии;
- бизнес-правила;
- состояния сущностей и переходы между ними;
- зависимости между функциональными блоками;
- критерии приёмки на уровне поведения продукта;
- юридические вопросы и реестр юридических решений;
- продуктовые метрики;
- подготовку следующей итерации до того, как разработчик приступит к ней.

### 2.2. Разработчик

Разработчик отвечает за:

- техническую реализацию;
- архитектуру в рамках уже определённого ФТЗ стека и принятых архитектурных поправок;
- каркас приложения;
- инфраструктуру и Docker;
- API и модели данных;
- интеграционную реализацию;
- тесты;
- технические решения;
- реализацию требований подготовленной аналитиком итерации.

### 2.3. Рабочий принцип

> **Аналитик должен идти примерно на одну итерацию впереди разработчика.**

Пока разработчик реализует текущую итерацию, аналитик полностью готовит следующую по Definition of Ready из этого документа.

Разработчик не должен самостоятельно закрывать продуктовые развилки, которые относятся к зоне аналитика: границы сценария, бизнес-правила, раскрытие данных, юридические условия, критерии успеха, смысл статусов и продуктовые исключения.

## 3. Продуктовая логика

Исходная идея ФТЗ сохраняется: **«Агрополия» должна превратить существующий «Метеомониторинг» из сервиса эпизодического просмотра погоды в ежедневную рабочую среду агрария.**

Центральная сущность продукта — **поле**.

Основной продуктовый цикл:

```text
Поле → риск/состояние → действие → фиксация результата → накопление знания
```

Коммерческий цикл появляется позже:

```text
Подтверждённая проблема → потребность → запрос → лид → предложение партнёра
```

Первая версия продукта не должна одновременно пытаться проверить все гипотезы платформы. Сначала необходимо подтвердить самостоятельную ценность базового рабочего цикла хозяйства; затем — ценность сообщества; затем — коммерческий контур; затем — регулируемые процессы.

# 4. Внутренняя дорожная карта

## 4.1. Итерация 0 — фундамент

**Цель:** создать техническую основу продукта, пользователя, организацию, права и возможность войти в систему.

Эта итерация уже преимущественно находится в зоне разработчика. Аналитическая задача — не расширять её новыми продуктовым контурами, а обеспечить однозначность базовых правил пользователя, организации, ролей и согласий.

### Входит

P0 по ФТЗ:

- `FR-AUTH-01` — Вход по номеру телефона;
- `FR-AUTH-02` — Связывание с учётной записью «Метеомониторинга»;
- `FR-AUTH-03` — Регистрация нового хозяйства;
- `FR-ORG-01` — Профиль организации;
- `FR-ORG-02` — Роли и права;
- `FR-ORG-03` — Приглашение по ссылке и по телефону;
- `FR-ORG-04` — Запрос доступа к существующей организации;
- `FR-PRIV-01` — Раздельные согласия.

### Особое правило по `FR-PRIV-01`

`FR-PRIV-01` может реализовываться поэтапно.

На Итерации 0 необходимы:

- архитектура согласий;
- журнал версий согласий;
- фиксация факта согласия и отзыва;
- те согласия, которые действительно нужны уже существующему функционалу.

Согласия на функции, которых пока нет, не должны искусственно заставлять реализовывать соответствующие продуктовые контуры раньше времени. Например, согласие на публикацию наблюдений, передачу запроса партнёрам или маркетинговые уведомления должно появляться вместе с соответствующей функцией и её бизнес-правилами.

### Не входит

- полноценный продуктовый onboarding `FR-AUTH-04`;
- поля, наблюдения, задачи и уведомления как рабочий продуктовый цикл;
- сообщество;
- рынок и лиды;
- регулируемый контур.

### Точка решения / расхождение с текущим I-0

`OPEN QUESTION I0-01`: текущий документ `docs/i-0/iteration-0-scope-and-plan-2026-10-01.md` сознательно описывает более узкий технический I-0 и прямо оставляет вне scope `FR-AUTH-02`, приглашения и `FR-ORG-04`, а часть `FR-AUTH-01`, `FR-AUTH-03`, `FR-ORG-02`, `FR-PRIV-01` считает только foundation/partial.

Необходимо решить, как трактовать это расхождение:

- вариант A — текущий I-0 остаётся техническим foundation-slice, а незакрытые FR из аналитической Итерации 0 завершаются до/в начале Итерации 1;
- вариант B — расширить критерий завершения внутренней Итерации 0 до полного набора FR выше отдельным изменением плана.

**До решения нельзя автоматически считать перечисленные FR полностью закрытыми только потому, что foundation уже реализован.**

## 4.2. Итерация 1 — первый рабочий MVP

**Статус в этой дорожной карте:** следующий основной продуктовый контур после фундамента.

**Основная аудитория:** существующее хозяйство, уже зарегистрированное в «Метеомониторинге».

**Основной сквозной сценарий:**

```text
Вход → хозяйство → поля → состояние поля → наблюдение → задача → выполнение → журнал
```

**Цель:** проверить, способен ли продукт стать ежедневным рабочим инструментом хозяйства, а не просто новым интерфейсом просмотра погоды.

### Входит — 25 функциональных требований

| Модуль | Требования |
|---|---|
| AUTH | `FR-AUTH-04` |
| FIELD | `FR-FIELD-01`, `FR-FIELD-03`, `FR-FIELD-04`, `FR-FIELD-05`, `FR-FIELD-07` |
| OBS | `FR-OBS-01`, `FR-OBS-02`, `FR-OBS-05` |
| OFFLINE | `FR-OFFLINE-01`, `FR-OFFLINE-02`, `FR-OFFLINE-03`, `FR-OFFLINE-05` |
| CATALOG | `FR-CATALOG-01`, `FR-CATALOG-02` |
| TASK | `FR-TASK-01`, `FR-TASK-02`, `FR-TASK-03`, `FR-TASK-05`, `FR-TASK-06`, `FR-TASK-07` |
| NOTIF | `FR-NOTIF-01`, `FR-NOTIF-02`, `FR-NOTIF-03`, `FR-NOTIF-04` |

**Итого: 25 FR.**

### Что должно быть доказано этой итерацией

- хозяйство открывает приложение не только ради погоды;
- поле становится рабочей точкой входа;
- состояние/риск приводит к действию;
- наблюдение можно быстро зафиксировать в поле;
- задача доходит до выполнения;
- выполненная работа сохраняется в журнале;
- уведомления действительно возвращают пользователя к работе в приложении.

### Не входит

В первую итерацию сознательно **не входят**:

- социальная сеть;
- вопросы соседям;
- рынок;
- лиды;
- партнёры;
- платежи;
- пчеловоды;
- «Сатурн»;
- полноценный бот;
- ИИ-ассистент;
- ИИ-диагностика;
- регулируемый сценарий применения препаратов.

`FR-TASK-04` «Обработка препаратом» пока не включается, потому что тянет зависимую цепочку:

```text
Госкаталог → правила применения → пчеловоды → юридические требования → Сатурн
```

Первая итерация ориентирована на хозяйства, уже имеющиеся в «Метеомониторинге», поэтому ручное создание/рисование и импорт новых полей (`FR-FIELD-02`) не должны задерживать запуск первого рабочего MVP.

### Критические зависимости до старта разработки

- подтверждённые данные/контракты `INT-METEO-01…05` в необходимой части;
- правила источника истины по пользователю, организации, ролям и полям;
- состав карточки поля и фактическая доступность её данных;
- юридически допустимый набор ПДн/геоданных/согласий;
- события продуктовой аналитики для диагностических метрик Итерации 1.

## 4.3. Итерация 2 — сообщество

**Цель:** проверить, возникает ли ценность от взаимодействия хозяйств между собой.

**Основной сценарий:**

```text
Наблюдение → публикация → соседи → вопрос → ответ → лучший ответ → решено
```

### Входит

Соответствующие P0-требования контуров:

- FEED — публичная лента и маршрутизация релевантных публикаций;
- QA — вопросы, SOS, ответы, эскалации, статусы;
- REP — репутация, значки, экспертность;
- MOD — жалобы, ограничения, автофильтры, верификация;
- связанные `PRIV`, `OBS`, `AUTH`, необходимые именно для публичного взаимодействия.

Точный перечень FR должен быть зафиксирован отдельной матрицей `P0 → внутренняя итерация` до передачи Итерации 2 разработчику. До этого документация не должна незаметно трактовать весь модуль как автоматически включённый.

### Аналитические задачи до разработки

- [ ] определить различие приватной и публичной записи;
- [ ] зафиксировать правила публикации наблюдения/вопроса;
- [ ] определить механизм обезличивания координат и пользовательское объяснение;
- [ ] определить радиус «соседей» и его изменение;
- [ ] определить маршрутизацию вопроса;
- [ ] определить эскалацию при отсутствии ответа;
- [ ] определить статус эксперта и процедуру его получения;
- [ ] определить лучший ответ;
- [ ] определить статус `Решено` и последующий outcome;
- [ ] определить жалобы и причины;
- [ ] определить модерационные действия и SLA;
- [ ] определить правила блокировок/ограничений и апелляций, если они нужны в этой версии;
- [ ] определить поведение при недостаточном количестве релевантных пользователей.

### Продуктовый риск

> **Социальная механика не работает без достаточного количества активных пользователей.**

До реализации должны быть определены правила поведения системы при недостаточной плотности аудитории: расширение радиуса, район/республика, подключение экспертов, показ отсутствия аудитории, допустимые fallback-сценарии. Эти правила не должны появиться как техническое решение разработчика без продуктового решения аналитика.

## 4.4. Итерация 3 — коммерческий контур

**Цель:** проверить бизнес-модель платформы.

**Основной сценарий:**

```text
Проблема → запрос предложений → лид → ответ партнёра → выбор предложения
```

### Входит

- соответствующие P0 `MKT`;
- соответствующие P0 `LEAD`;
- соответствующие P0 `PARTNER`;
- связанные требования приватности и согласий.

Платежи внутри платформы на этом этапе **не являются обязательным условием** проверки гипотезы.

### Аналитик должен определить до разработки

- [ ] что считается квалифицированным лидом;
- [ ] какие данные передаются партнёру;
- [ ] какие данные никогда не передаются автоматически;
- [ ] когда раскрывается контакт пользователя;
- [ ] сколько партнёров получает запрос;
- [ ] правила маршрутизации;
- [ ] срок ответа партнёра;
- [ ] что считается ответом;
- [ ] что считается завершённым лидом;
- [ ] когда возникает платное событие;
- [ ] что происходит при отсутствии ответа;
- [ ] каким образом пользователь сравнивает предложения;
- [ ] какие согласия необходимы до создания/маршрутизации лида.

### Главная продуктово-коммерческая гипотеза

> Готов ли партнёр платить за лид, сформированный из реальной подтверждённой потребности хозяйства?

Если ответ на эту гипотезу можно получить через договорные пилоты и учёт событий вне встроенного платежного контура, платежи не должны задерживать проверку.

## 4.5. Итерация 4 — регулируемый контур

**Цель:** добавить регулируемые и юридически чувствительные агротехнологические процессы.

**Основной сценарий:**

```text
Планирование обработки → препарат → проверка правил → уведомление → выполнение → фиксация → Сатурн
```

### Входит

- применение СЗР, включая `FR-TASK-04`;
- Госкаталог (`FR-CATALOG-03` и необходимые интеграции);
- сроки ожидания и связанные правила;
- уведомления пчеловодов (`BEE`);
- географический поиск пасек;
- документы/сведения для ФГИС «Сатурн» (`SATURN`);
- соответствующие функции бота;
- доказательная фиксация выполнения.

### Условие входа

Этот контур реализуется только после закрытия необходимых юридических вопросов и фиксации источников актуальных правил. Правила, зависящие от НПА/регламентов, не должны быть придуманы разработчиком или закреплены в коде без подтверждённого источника решения.

# 5. Отложенные P0 по продуктовым контурам

Все перечисленные ниже требования **остаются P0 по ФТЗ**. Раздел объясняет только, почему их реализация следует после первого рабочего MVP.

## 5.1. Развитие базового хозяйства

Типовые требования этого блока: P0, которые усиливают базовый контур, но не обязательны для первого доказательства цикла `поле → состояние → действие → журнал`, например ручное создание/импорт полей, полная история поля, шаблоны операций, отчётные выгрузки, расширенные административные функции.

Почему позже: сначала нужно доказать, что хозяйства используют базовый цикл на уже существующих данных «Метеомониторинга». Расширение способов заведения данных и вспомогательных функций не должно задерживать проверку ежедневной ценности.

`OPEN QUESTION BASE-01`: точный перечень этого блока должен быть закрыт артефактом «Матрица всех P0 → внутренние итерации».

## 5.2. ИИ-диагностика

Связанные P0: `FR-OBS-04`, `FR-ML-01…04`, `FR-AI-01`, связанные точки `FR-QA-08` и датасетные функции.

Почему позже: базовое наблюдение обладает самостоятельной ценностью без автоматического диагноза. ИИ добавляет юридические, инфраструктурные и продуктовые риски: качество модели, передача фото, ограничение ответственности, объяснимость и зависимость от провайдера. Его следует включать после проверки самого поведения «заметил → зафиксировал → действую».

## 5.3. Сообщество

Связанные P0: `FEED`, `QA`, `REP`, `MOD`, а также необходимые `PRIV/OBS/AUTH`.

Почему позже: сообщество имеет ценность только поверх достаточной базы активных хозяйств и наблюдений. Если базовый цикл не используется, социальный слой не исправит основную проблему удержания.

## 5.4. Коммерческий контур

Связанные P0: `MKT`, `LEAD`, `PARTNER` и необходимые требования приватности/согласий.

Почему позже: качественный лид должен рождаться из реально используемого продукта и подтверждённой потребности, а не из искусственного трафика. Сначала нужен рабочий продукт и, желательно, накопленная активность/проблемы; затем проверяется монетизация.

## 5.5. Регулируемый контур

Связанные P0: `FR-TASK-04`, `FR-CATALOG-03`, `BEE`, P0 `SATURN`, связанные `BOT/NOTIF`.

Почему позже: этот контур требует актуальных правовых решений, достоверного Госкаталога, точных данных поля/обработки, доказательной фиксации и устойчивого базового журнала работ. Ошибка здесь несёт больший риск, чем отсутствие функции в первой версии.

# 6. P0 на пересмотр

> «На пересмотр» не означает изменение P0. До отдельного продуктового решения исходный приоритет остаётся тем, который указан в ФТЗ.

| ID | Название по ФТЗ | Исходный приоритет | Предлагаемое отношение | Причина пересмотра | Когда снова актуально |
|---|---|---:|---|---|---|
| `FR-FIELD-08` | Публикуемая точность прогнозов | P0 | Не блокировать Итерацию 1 | Для первого рабочего цикла важнее сами данные поля/рисков и действие; методика публичной точности требует отдельной договорённости о факте и расчёте | Когда определена методика M11/факт-прогноз и есть достаточный объём данных |
| `FR-OBS-03` | Голос в пост | P0 | Отложить как ускоритель ввода | Базовое наблюдение можно создать фото/текстом; STT добавляет внешнюю зависимость | Когда базовый сценарий наблюдения подтверждён и голос реально снимает friction |
| `FR-OBS-04` | ИИ-гипотезы по фото | P0 | Вынести в отдельный ИИ-срез | Наблюдение ценно без ИИ; есть юридические и провайдерные риски | После выбора допустимого ML-провайдера/режима данных и проверки потребности |
| `FR-QA-08` | ИИ-ответ как первый комментарий | P0 | Не считать обязательным для запуска сообщества | Может маскировать недостаточную живость реального сообщества и зависит от `FR-AI-01` | После запуска QA и понимания дефицита ответов; при готовом безопасном AI-контуре |
| `FR-NOTIF-07` | Ночной режим | P0 | Проверить, нужен ли отдельный FR сверх общих правил тишины | Частично пересекается с `FR-NOTIF-01/06`; важно не дублировать продуктовую логику | Если после спецификации уведомлений остаётся отдельное поведение/приёмка ночью |
| `FR-AI-01` | Ассистент по данным хозяйства | P0 (базовый), P1 (расширенный) | Не блокировать первый рабочий MVP | Основной цикл может работать без чат-ассистента; AI добавляет ответственность и внешнюю обработку данных | После стабилизации данных поля/справочников и юридической модели AI |
| `FR-BOT-04` | Фото-вопрос из бота | P0 | Перенести после базового QA/OBS | Бот — дополнительный канал уже существующего сценария, а не первичная проверка ценности | Когда QA/наблюдения работают в основном приложении и определена роль бота |
| `FR-BOT-05` | Объявления ЛПХ | P0 | Перенести к коммерческому/ЛПХ контуру | Не относится к проверке рабочего цикла существующего хозяйства | Когда запускается рынок/ЛПХ и определены модерация/правила объявлений |
| `FR-ADMIN-04` | Тарифы и начисления | P0 (учёт), P1 (биллинг) | Не блокировать проверку лида при возможности договорного пилота | Платность можно проверить вне встроенного биллинга; нужен сначала факт ценности лида | Когда определена тарифная модель и событие тарификации |
| `FR-ADMIN-06` | Экспорт датасетов НИОКР | P0 | Не блокировать Итерацию 1 | Нужен только когда накоплены размеченные сигналы/ИИ-гипотезы; базовый журнал может жить без него | Когда запущены `FR-OBS-07`/ML и сформирован процесс НИОКР |

Общая логика: **функция не должна задерживать проверку основной продуктовой гипотезы, если без неё первый рабочий цикл уже обладает самостоятельной ценностью.**

# 7. Definition of Ready аналитической итерации

Итерация считается аналитически подготовленной к передаче разработчику, когда определены:

- [ ] 1. цель;
- [ ] 2. целевой пользователь;
- [ ] 3. основной сквозной сценарий;
- [ ] 4. границы — входит / не входит;
- [ ] 5. требования FR;
- [ ] 6. бизнес-правила;
- [ ] 7. необходимые данные;
- [ ] 8. состояния ключевых сущностей;
- [ ] 9. переходы состояний;
- [ ] 10. роли и права;
- [ ] 11. исключительные ситуации;
- [ ] 12. поведение при ошибках;
- [ ] 13. зависимости;
- [ ] 14. юридические ограничения;
- [ ] 15. события продуктовой аналитики;
- [ ] 16. критерии приёмки;
- [ ] 17. критерий успешности самой итерации.

Если хотя бы один пункт влияет на поведение пользователя или бизнес-результат и не определён, он фиксируется как `OPEN QUESTION` с владельцем решения. Разработчик не должен самостоятельно «додумывать» такое решение в коде.

# 8. Зависимости от «Метеомониторинга»

## 8.1. Принцип

> **«Метеомониторинг» остаётся источником метеоданных, ГИС и существующих расчётов. «Агрополия» является надстройкой, а не заменой.**

Дорожная карта описывает потребность продукта в данных. Конкретный API/событийный контракт проектируется отдельно после подтверждения доступности источника и владельца данных.

## 8.2. Минимум для Итерации 1

| Данные | Для какого сценария | Направление | Источник истины | Критичность | Статус контракта | Открытый вопрос |
|---|---|---|---|---|---|---|
| Пользователь | вход/связывание существующего пользователя | Meteo → Agropolia | OPEN QUESTION: модель учётной записи | BLOCKER | OPEN | По какому ключу связываем; существует ли API |
| Организация | вход → хозяйство | Meteo → Agropolia | Meteo для уже зарегистрированных хозяйств | BLOCKER | OPEN | Как идентифицируется организация; конфликт/дубликат |
| Роли | доступ к хозяйству/полям | Meteo → Agropolia | Требуется согласованный маппинг | HIGH | OPEN | Как комбинированные роли переводятся в роли Агрополии |
| Поля | список/карта/карточка поля | Meteo → Agropolia | Meteo для существующих хозяйств | BLOCKER | OPEN | Формат идентификатора, изменяемость, удаление/архив |
| Контуры | карта поля и привязка состояния | Meteo → Agropolia | Meteo | BLOCKER | OPEN | Формат геометрии, система координат, version/update semantics |
| Культуры | карточка, фильтры, наблюдения, задачи | Meteo → Agropolia | Meteo/единый справочник | HIGH | OPEN | Идентификаторы и версии справочника |
| Станции | источник текущей погоды | Meteo → Agropolia | Meteo | HIGH | OPEN | Правило привязки/смены станции и fallback |
| Текущая погода | карточка поля | Meteo → Agropolia | Meteo | BLOCKER | OPEN | Набор параметров, timestamp, freshness/SLA |
| Прогноз | карточка, планирование задачи | Meteo → Agropolia | Meteo/его провайдер | HIGH | OPEN | Горизонт и состав прогноза |

| Риски | состояние поля, уведомление | Meteo → Agropolia | Meteo | BLOCKER | OPEN | Уровни, confidence, причины, изменение/отмена сигнала |
| ΣT | карточка поля | Meteo → Agropolia | Meteo при одинаковых входных данных | HIGH | OPEN | Что именно отдаётся: результат или исходные данные |
| Фенофаза | карточка поля | Meteo → Agropolia | OPEN QUESTION | HIGH | OPEN | Расчётная/ручная фаза, источник и актуализация |
| Рекомендации/техкарты | карточка поля, создание задачи — если входят в UX | Meteo → Agropolia | Meteo | MEDIUM/HIGH | OPEN | Нужны ли в обязательном составе Iteration 1 card; структура данных |

### 8.3. Блокирующий риск

Неопределённость `INT-METEO-01…05` является **блокирующим риском Итерации 1**. В самом ФТЗ этот риск также отмечен как критичный. До начала полноценной реализации Итерации 1 должны быть подтверждены хотя бы продуктовые контракты данных: что существует, кто владелец истины, какой идентификатор стабилен, какая свежесть нужна, как трактуются ошибки/недоступность.

Не следует проектировать конкретный REST/шину/endpoint в этом документе до согласования технического контракта.

# 10. Метрики первой итерации

Глобальные KPI ФТЗ (`M1…M11`) сохраняются. Ниже — диагностические показатели Итерации 1, которые помогают понять, **где именно работает или ломается базовый рабочий цикл**.

| Метрика Итерации 1 | Что проверяет | Событие / источник | Когда измерять | Как интерпретировать |
|---|---|---|---|---|
| Доля вошедших пользователей, открывших хотя бы одно поле | Понятна ли ценность после входа | `app_open` + `field_card_open` (`EV-01`, `EV-05`) | С первых тестовых когорт | Низкое значение = проблема входа/навигации/релевантности поля, а не обязательно удержания |
| Доля активных хозяйств, которые открывают карточку поля | Стало ли поле рабочей точкой входа | `EV-05` по org | После появления реальных полей | Связывает продуктовый цикл с `M1/M2`; целевой % — `OPEN PRODUCT DECISION` после первых данных |
| Число наблюдений на активное хозяйство | Используется ли скаутинг | `EV-30` | После стабилизации сценария наблюдения | Ноль при высокой активности карточки = наблюдение не нужно/слишком сложно/не вовремя |
| Доля хозяйств, создавших хотя бы одну задачу | Переходит ли состояние поля в действие | `EV-50` | После запуска TASK | Ключевой мост `поле/риск → действие` |
| Доля созданных задач, доведённых до выполнения | Закрывается ли рабочий цикл | `EV-50` + `EV-51` | Когортно, с учётом срока задачи | Низкая доля может означать неверную модель статусов, UX или отсутствие реальной пользы |
| Возврат после утреннего дайджеста | Работает ли ежедневный повод | `EV-10` + последующий `app_open/field_card_open` | После запуска `FR-NOTIF-02` | Связь с `M1`; окно атрибуции требуется определить аналитически |
| Возврат после уведомления о риске ОЯ | Работает ли срочный триггер | `EV-11` + последующее действие | После реальных ОЯ/рисков | Важно различать open push и полезное действие после него |
| Количество активных дней хозяйства за неделю | Формируется ли привычка | агрегат `EV-01`/полезных действий по org | Недельными когортами | Диагностирует движение к M1/retention без подмены глобального KPI |

### 10.1. Требующие продуктового решения определения

До начала измерения аналитик должен определить:

- что считать «вошедшим пользователем» для знаменателя;
- что считать «активным хозяйством»;
- какое окно атрибуции использовать после push/дайджеста;
- какие действия считаются полезным возвратом, а не просто открытием;
- как учитывать тестовые/служебные организации;
- с какого момента начинается когорта Итерации 1.

Целевые проценты **не придумываются** до появления первых данных, если они не заданы ФТЗ. Такие значения фиксируются как `OPEN PRODUCT DECISION` и устанавливаются после первых когорт/полевых тестов.

# 11. Контрольные точки между итерациями

Техническое завершение предыдущей итерации само по себе не является основанием автоматически начинать следующий крупный продуктовый контур.

## 11.1. Gate после Итерации 1

Проверить:

- [ ] пользуются ли хозяйства карточкой поля;
- [ ] создают ли наблюдения;
- [ ] создают ли задачи;
- [ ] доводят ли задачи до выполнения;
- [ ] возвращаются ли по уведомлениям;
- [ ] есть ли повторное использование в разные дни недели;
- [ ] какие этапы сквозного сценария имеют наибольший отвал.

**Решение:** если базовый рабочий цикл не используется, сначала выяснить причину и исправить базовую ценность, а не автоматически наращивать продукт социальной сетью.

## 11.2. Gate после Итерации 2

Проверить:

- [ ] публикуются ли наблюдения;
- [ ] задаются ли вопросы;
- [ ] хватает ли аудитории для получения ответов;
- [ ] сколько времени проходит до первого ответа;
- [ ] как часто требуется эскалация;
- [ ] закрываются ли вопросы как решённые;
- [ ] помогает ли лучший ответ по последующей оценке.

## 11.3. Gate после Итерации 3

Проверить:

- [ ] возникают ли запросы предложений;
- [ ] отвечают ли партнёры;
- [ ] выбирают ли пользователи предложения;
- [ ] открывают ли контакты / совершают целевое действие;
- [ ] считают ли партнёры лид ценным;
- [ ] готовы ли партнёры платить;
- [ ] какая модель тарификации соответствует фактической ценности.

# 12. Рабочий процесс аналитик ↔ разработчик

## 12.1. До итерации

Аналитик передаёт разработчику подготовленный пакет по Definition of Ready.

Минимальный пакет:

- основной сценарий;
- scope / out of scope;
- FR и зависимости;
- бизнес-правила;
- состояния/переходы;
- роли;
- ошибки/исключения;
- юридические ограничения;
- события аналитики;
- критерии приёмки;
- открытые вопросы с владельцами.

## 12.2. В начале итерации

Аналитик и разработчик совместно проходят основной сквозной сценарий от начала до конца и проверяют, что у разработчика нет необходимости принимать продуктовые решения вместо аналитика.

## 12.3. Во время итерации

Новые продуктовые решения не остаются только в чате или устной договорённости.

Они фиксируются:

- в соответствующей аналитической спецификации;
- в журнале решений;
- в реестре юридических решений;
- при необходимости — отдельным изменением ФТЗ/ADR, если решение затрагивает соответствующую область.

## 12.4. В конце итерации

Приёмка проводится:

1. сначала по основному сквозному пользовательскому сценарию;
2. затем по отдельным FR и исключениям;
3. затем по событиям аналитики и способности измерить критерий успешности.

После завершения документация приводится в соответствие с фактически принятыми решениями.

# 15. Проверка внутренней непротиворечивости

## 15.1. Приоритеты ФТЗ

- ни один P0/P1/P2 в этом документе не переопределяется;
- внутренние итерации не трактуются как новый продуктовый приоритет;
- таблица «P0 на пересмотр» не меняет исходные P0.

## 15.2. Логика последовательности

```text
Итерация 0: идентичность + организация + права + согласия
    ↓
Итерация 1: поле + состояние + наблюдение + задача + журнал + уведомления
    ↓
Итерация 2: публикация + соседи + вопрос + ответ + модерация
    ↓
Итерация 3: потребность + RFQ + лид + партнёрское предложение
    ↓
Итерация 4: СЗР + регуляторные проверки + пчеловоды + Сатурн
```

Каждый следующий контур опирается на подтверждённые сущности/поведение предыдущего:

- сообществу нужны активные хозяйства и наблюдения;
- коммерции нужны реальные потребности/проблемы и доверие пользователя;
- регулируемому контуру нужен устойчивый журнал работ, точные поля и закрытые юридические правила.

## 15.3. Проверка состава Итерации 1

Указанный набор содержит ровно **25 функциональных требований**: 1 AUTH + 5 FIELD + 3 OBS + 4 OFFLINE + 2 CATALOG + 6 TASK + 4 NOTIF.

## 15.4. Что документ намеренно не делает

- не проектирует конкретные API `INT-METEO-*`;
- не меняет архитектурные решения разработчика;
