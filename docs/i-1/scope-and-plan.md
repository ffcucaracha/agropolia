# I-1 — первый автономный web/PWA slice (утверждён к реализации)

Дата: 2026-11-11. Ветка: `i-1`, база: `main@e4e6628`.
Источники: `docs/ANALYTICS_ROADMAP.md`, ФТЗ v1.0, `docs/ftz-architecture-amendments-2026-10-01.md` и `docs/i-0/`.

## Пользовательская цель
`email OTP → хозяйство → вручную созданное поле → приватное наблюдение → задача → выполнение → журналы`.
Независимо от `INT-METEO-01…05`. Ни внешних mock API, ни фиктивных погодных показателей.

## Scope
- Минимальная часть **FR-FIELD-02** (явное исключение из исходной матрицы I-1): ручное поле без геометрии; название, культура, площадь, дата сева. `source=manual` и nullable `meteo_field_id` для будущей интеграции. FR-FIELD-04/05 — только карточка и список, не метеосводка/карта.
- **FR-OBS-01/02/05**: приватное наблюдение на поле, текст, тип, фото, дата/автор, фильтруемый журнал. Без STT, ML и публичных публикаций.
- **FR-TASK-01/02/03/05/06**: owner-only задачи по полям и из наблюдений, допустимая машина состояний, блокировка с причиной, подтверждение с фото, журнал выполненных работ. Препараты/FR-TASK-04 исключены.
- **FR-OFFLINE-01/02/03/05** — web-подмножество: IndexedDB, исходящая очередь, UUIDv7 client_op_id, optimistic concurrency с base_version, серверный журнал sync, reconnect/visibility sync. Никакой гарантии фоновой работы после закрытия браузера.
- **FR-NOTIF-01 + FR-TASK-07** — in-app уведомления об изменении задач/сроках, пользовательские настройки категорий. Без push/SMS/бота, Meteo-digest.
- Carry-over в необходимой части: FR-ORG-02 (права owner на новые ресурсы), FR-PRIV-01 (геоданные/consent, если запрошены). FR-AUTH-02 остаётся внешним блокером.

## Архитектура
- FastAPI modular monolith, один PostgreSQL с отдельными schemas по bounded context, Alembic; auth context из I-0.
- Состояние + запись change log/outbox в одной транзакции; NATS JetStream, идемпотентный notify consumer. Redis не task broker.
- Объекты из другого `org_id` отвечают 404; в payload `org_id` не доверяем.
- Никакого универсального LWW: `base_version`/CAS, `CONFLICT` при несовпадении.
- Media приватны; production storage требует S3-compatible provider и одобренного размещения/секретов.
- Веб-клиент использует существующие auth/api abstractions и отдельную реализацию LocalPersistence для IndexedDB.

## Вертикальный план
1. Поля + backend/frontend; миграции; tenant tests.
2. Sync foundation + IndexedDB; повторная отправка/конфликты; тесты.
3. Наблюдения + приватные медиа + журнал; E2E.
4. Задачи + состояния + WorkLog + экран Сегодня; E2E.
5. In-app notification center/settings + notify worker; tests.
6. Полный browser E2E с реальными API/DB, security regression и CI.

## Контроль приёмки
- Регистрация I-0 не нарушена, login → создание поля.
- Поле/наблюдение/задача остаются после перезагрузки; нет межорганизационных утечек.
- Offline создание/повтор отправки не дублирует; outdated base_version → CONFLICT; состояние done не откатывается.
- Выполненная задача ровно один раз появляется в журнале; уведомления не дублируются при redelivery.
- В UI нет фиктивных погодных, ML, соцсетевых и регулируемых функций.
- `pytest` интеграционные и security тесты на настоящих сервисах, Playwright E2E против настоящего backend/database.

## Blockers / отдельные решения
- `INT-METEO-01…05` не специфицированы, все Meteo-dependent FR остаются открыты.
- Полнота справочников культур/операций требует утверждённого источника; в автономном UI допустим свободный ввод культуры и типа операции вместо ложного «каталога Meteo».
- Полный FR-OBS-02 (video/voice/STT), мобильные background tasks, offline tiles, multi-user ORG-03, browser push — за пределами этого slice.
- Юридически утверждённые тексты согласий и production S3/PDn deployment требуют отдельной приёмки.
